# Accessible Video Analyzer

Hackathon project: given a video (YouTube link or upload), find which moments
contain visual information — diagrams, charts, on-screen text, demonstrations,
gestures — that a blind user listening to only the audio would miss.

Pipeline:

```
Video -> chunk (FFmpeg) -> extract frames (FFmpeg) -> extract audio (FFmpeg)
      -> transcript w/ timestamps (Whisper) -> detect changed frames (OpenCV)
      -> send only changed frames + transcript context to a vision LLM
      -> accessibility issues + timestamps
```

Step 6 (the vision LLM call) supports two interchangeable providers:
**Gemini** (default) or **Groq** (currently `meta-llama/llama-4-scout-17b-16e-instruct`,
which Groq hosts on their fast LPU inference). Switch between them with one
line in `.env` — no code changes needed.

Every step is its own FastAPI endpoint, matching the workflow 1:1, plus one
endpoint that runs the whole thing in one call.

## 1. Setup

```bash
cd access-video
python3 -m venv venv
source venv/bin/activate          # on Windows: venv\Scripts\activate
pip install -r requirements.txt
```

You'll also need `ffmpeg` installed and on your PATH (not a Python package):

- macOS: `brew install ffmpeg`
- Ubuntu/Debian: `sudo apt install ffmpeg`
- Windows: download from https://ffmpeg.org/download.html and add to PATH

Copy the env file and add your API key. Choose **one** of the two vision
providers for step 6:

```bash
cp .env.example .env
```

Then edit `.env`:

- **Gemini** (default): set `VISION_PROVIDER=gemini` and `GEMINI_API_KEY=...`
  (get a free key at https://aistudio.google.com/app/apikey).
- **Groq** (faster, free tier available, good if Gemini is rate-limited or
  "high traffic"): set `VISION_PROVIDER=groq` and `GROQ_API_KEY=...`
  (get a key at https://console.groq.com/keys). Uses
  `meta-llama/llama-4-scout-17b-16e-instruct` by default, a vision-capable
  model Groq hosts.

You only need the API key for whichever provider you set in `VISION_PROVIDER`
— the other one can stay as the placeholder text.

## 2. Run

```bash
uvicorn app.main:app --reload --port 8000
```

- Interactive API docs (Swagger): http://localhost:8000/docs
- Minimal demo UI: http://localhost:8000/static/index.html

The demo UI lets you paste a YouTube link or upload a file, click "Run Full
Pipeline", and see the flagged frames with thumbnails.

## 3. Endpoints

All return JSON. `{job_id}` is generated by the upload step and reused for
every subsequent call.

| Step | Method & path | What it does |
|---|---|---|
| 1 | `POST /api/v1/upload/file` (multipart file) | Upload a video file directly. Returns `job_id`. |
| 1 | `POST /api/v1/upload/youtube` (`{"youtube_url": "..."}`) | Download a YouTube video via yt-dlp. Returns `job_id`. |
| 2 | `POST /api/v1/chunk/{job_id}?chunk_seconds=1` | Split video into N-second `.mp4` chunks via FFmpeg. |
| 3 | `POST /api/v1/extract-frames/{job_id}?interval_seconds=2` | Extract one frame every N seconds via FFmpeg. |
| 3 | `POST /api/v1/extract-audio/{job_id}` | Extract a 16kHz mono WAV audio track via FFmpeg. |
| 4 | `POST /api/v1/transcribe/{job_id}` | Transcribe the audio with Whisper (faster-whisper), with timestamps. |
| 5 | `POST /api/v1/detect-changes/{job_id}?threshold=4.0` | Use OpenCV to keep only frames that changed meaningfully vs. the previous one. |
| 6 | `POST /api/v1/analyze/{job_id}?provider=groq&model=...` | Send changed frames + transcript context to the chosen vision model; get back accessibility verdicts. `provider` and `model` are optional — defaults come from `.env`. |
| — | `POST /api/v1/pipeline/run/{job_id}?vision_provider=groq` | Runs steps 2-6 in one call. `vision_provider`/`vision_model` are optional overrides. |
| — | `GET /api/v1/status/{job_id}` | Check what's been completed for a job. |

### Example: full pipeline via curl

```bash
# 1. Upload
curl -X POST http://localhost:8000/api/v1/upload/file \
  -F "file=@/path/to/video.mp4"
# => {"job_id": "abc-123", ...}

# Run everything else in one call
curl -X POST "http://localhost:8000/api/v1/pipeline/run/abc-123"
```

Final response shape (the actual deliverable — array of problem frames):

```json
{
  "job_id": "abc-123",
  "duration_seconds": 95.2,
  "num_chunks": 96,
  "num_frames_extracted": 48,
  "num_changed_frames_sent_to_gemini": 14,
  "num_transcript_segments": 22,
  "accessibility_issues": [
    {
      "frame_index": 6,
      "timestamp": 12.0,
      "frame_path": "app/storage/jobs/abc-123/frames/frame_000007.jpg",
      "issue_type": "diagram_or_chart",
      "reason": "A bar chart comparing quarterly revenue is shown but never described aloud.",
      "change_score": 18.4
    }
  ]
}
```

## 4. Design notes / why things are built this way

- **Job store**: a simple JSON file per job under `app/storage/jobs/{job_id}/state.json`.
  No database needed for a hackathon; swap for Redis/Postgres later if you
  need concurrency beyond a single process or multi-instance deployment.
- **Frame extraction reads from the source video**, not from the per-second
  chunks. This keeps timestamps simple (frame N is always at `N * interval`
  seconds) and avoids needing to stitch frame timestamps back together
  across chunk boundaries. The chunking step (step 2) is still implemented
  as you asked, and chunk files are saved — useful if you want to display a
  scrubber, do chunk-level processing later, or feed chunks somewhere else.
- **Chunking always re-encodes** (rather than the much faster `-c copy`).
  This matters: FFmpeg's segment muxer can only cut on existing keyframes
  in copy mode, so requesting 1-second chunks on a video with a 5-second
  keyframe interval would silently produce wrong-length chunks. Re-encoding
  with `-force_key_frames` guarantees exact chunk boundaries. It's slower,
  so for long videos you may want to parallelize this or skip it if you
  don't end up needing the chunk files downstream.
- **Frame diffing (step 5)** converts consecutive frames to grayscale,
  blurs slightly to ignore compression noise, thresholds the pixel-wise
  difference, and computes what percent of pixels changed. Anything above
  `FRAME_DIFF_THRESHOLD` (default 4%) is kept. Tune this in `.env` — lower
  catches more subtle changes (more Gemini calls, higher cost), higher
  misses subtle but meaningful changes (cheaper, faster).
- **Gemini gets transcript context, not just the image.** Each changed
  frame is paired with whatever was said in a +/-3 second window around it
  (configurable in `app/routers/analyze_router.py`). This lets Gemini
  correctly skip frames where a diagram is on screen but the narrator is
  already describing it verbally — otherwise you'd get false positives on
  every slide.
- **Batched Gemini calls**: frames are sent in batches of 8 (configurable
  in `app/services/gemini_analysis.py`) in a single request rather than one
  call per frame, to control cost and latency. Gemini returns strict JSON
  (`response_mime_type="application/json"`) so parsing is reliable.
- **Model / provider**: defaults to Gemini's `gemini-2.5-flash`, Google's
  current best price/performance multimodal model as of mid-2026. If Gemini
  is rate-limited, down, or you'd rather use Groq, set `VISION_PROVIDER=groq`
  in `.env` (and `GROQ_API_KEY`) — no code changes needed. The
  `app/services/vision_dispatcher.py` module routes step 6 to whichever
  provider is configured, and `app/services/gemini_analysis.py` /
  `groq_analysis.py` implement the same interface for each backend, so
  they're interchangeable. You can also override per-request via the
  `provider`/`model` query params on `/analyze/{job_id}` or
  `vision_provider`/`vision_model` on `/pipeline/run/{job_id}`, without
  touching `.env` at all.
  Note: Groq's vision models currently cap requests at 5 images each, so
  the Groq batch size defaults to 4 (vs. 8 for Gemini) in
  `app/services/groq_analysis.py`.
- **SDK**: uses `google-genai` (the current, actively maintained SDK) for
  Gemini, not the older `google-generativeai` package, which Google has
  deprecated in favor of this one. For Groq, uses the official `groq`
  Python package, which is OpenAI-chat-completions-compatible.

## 5. Known limitations (hackathon-scope, worth knowing)

- Single-process, in-memory-ish job store (JSON files) — fine for a demo,
  not for production concurrency.
- No background task queue: long videos block the HTTP request for the
  duration of the `pipeline/run` call. For a real product, move heavy steps
  (chunking, Whisper, Gemini) to a task queue (Celery/RQ/arq) and poll
  `/status/{job_id}`.
- Whisper's first run downloads the model weights from Hugging Face
  (a few hundred MB for the default `base` model) — make sure your machine
  has internet access the first time, after that it's cached locally.
- `yt-dlp` selects up to 720p video to keep things fast; raise the height
  cap in `app/services/ingest.py` if you need higher resolution frames.
- Gemini's verdicts are only as good as the prompt in
  `app/services/gemini_analysis.py` — tune `SYSTEM_INSTRUCTION` for your
  judging criteria (e.g. if you want it to also flag color-only information
  for color-blind users, or fast-flashing content for photosensitive users).
